# AMENDMENTS

A1. Recover trigger = a DECLINED CAPTURE. PayPal emits no webhook for it, so the app's own capture route handles the 422 (issues INSTRUMENT_DECLINED / TRANSACTION_REFUSED) synchronously: write a `payment.capture_declined` event to the DB, enqueue it, and return a clear result to the caller. Subscriptions and BILLING.SUBSCRIPTION.\* are OUT of scope. DEMO_MODE event injection and any signature bypass are REMOVED.
A2. "Simulate decline" control: env flag SANDBOX_NEGATIVE_TESTING (default false). When on, the capture route adds header PayPal-Mock-Response with mock_application_codes chosen by the caller (only INSTRUMENT_DECLINED or TRANSACTION_REFUSED allowed; anything else rejected, since INSUFFICIENT_FUNDS returned 403). Hard-disabled if the base URL is not sandbox. Events created this way carry source="sandbox_negative_testing", visible in the audit log. Never present them as real customer failures.
A3. Webhooks: handle CHECKOUT.ORDER.APPROVED, PAYMENT.CAPTURE.COMPLETED, PAYMENT.CAPTURE.REFUNDED, INVOICING.INVOICE.PAID. Verify signatures LOCALLY over the RAW BODY BYTES (never re-serialized JSON): signing string = transmission_id|transmission_time|webhook_id|crc32(raw body); RSA-SHA256 with the cert from cert_url. Rules: https only, no userinfo, host === "paypal.com" or endsWith(".paypal.com") (dot boundary); cache the cert; reject stale timestamps (tolerance from env); constant-time comparison where applicable; respond 2xx fast and process in BullMQ; dedupe by transmission/event ID in Redis (TTL) AND a unique DB constraint. Unverified events are stored as rejected and never processed.
A4. Polling reconciler (BullMQ repeatable job): GET /v2/checkout/orders/{id} and /v2/invoicing/invoices/{id} for non-terminal records; transition states idempotently. Do NOT use the Reporting API (403).
A5. LLM layer: OpenAI-compatible client; MODEL_PRIMARY and comma-separated MODEL_FALLBACKS from env, plus optional LLM_BASE_URL_2 / LLM_API_KEY_2 for a second provider. Rules: rule-first (policy engine decides before any model call); at most ONE model call per event; max 2 attempts per model with exponential backoff + jitter; honor retry-after; one JSON repair retry; per-day call counter in Redis/DB (env LLM_DAILY_BUDGET) surfaced via /readyz. If all models fail or the budget is exhausted -> event status WAITING_FOR_AI, visible and retryable, NEVER auto-acted. Responses cached by event ID so a retry never re-calls the model.
A6. Tests: Vitest for everything. A test-only LLM adapter may live ONLY under /tests. Live-model tests are a separate tagged suite (`pnpm test:live`) limited to 10 total model calls, with a hard abort if exceeded. CI never runs live tests.
A7. Security audit: run the security-audit skill in guidance/static mode via the available research subagent at the end of M1; report what the platform could not run. Also run semgrep, gitleaks, pnpm audit.

# M1 SCOPE (build only this)

1. Next.js (App Router, TS strict) scaffold, Tailwind, Drizzle + Postgres, Redis + BullMQ, Zod env validation at boot (app refuses to start on invalid env), pino logging, better-auth single-owner login (placeholder dashboard page only; no landing page, no 3D, no Hallmark UI work yet).
2. docker-compose: web, worker, db, redis with healthchecks; multi-stage Dockerfile, non-root; migrations run on boot; `docker compose up --build` works from a clean clone.
3. Schema: policies, events, proposals (agent output), actions (executed PayPal calls with idempotency key + request/response summary), approvals (single-use, expiring token), audit_log (append-only), webhook_deliveries, paypal_orders, paypal_invoices.
4. PayPal client: OAuth with token caching, orders create/get/capture, invoices create/send/get, refunds; PayPal-Request-Id on every mutating call; timeouts, bounded retries, circuit breaker.
5. Agent module: Zod schema {action: retry|offer|refund|escalate|none, amount|null, currency|null, message, confidence 0..1, reasoning}. Customer text is untrusted DATA wrapped in the prompt and can never alter policy or the schema.
6. Policy engine (pure TypeScript, no I/O): AUTO | NEEDS_APPROVAL | BLOCKED from policies in the DB. Fail closed: invalid, low-confidence, missing-data, or currency-mismatch input -> NEEDS_APPROVAL. Exhaustive Vitest including boundaries.
7. Executor: only it calls PayPal, only after AUTO or a valid approval. Idempotent, retry-safe, dead-letter state.
8. Pipeline end to end: declined capture -> event -> (rules) -> agent -> policy -> action or approval -> audit_log. Plus the webhook path and the polling reconciler.
9. First-run policies come from an onboarding API/form (no hardcoded limits in code).
